# Documentation and tracker notes for Claude

These notes supplement [AGENTS.md](../AGENTS.md) and the root [CLAUDE.md](../CLAUDE.md). They cover editing `docs/`, the tracker and the generated HTML.

## Markdown is the source; HTML is generated

- Edit Markdown only. `docs/html/` is generated by `npm run docs:build` (`scripts/docs/build.mjs`) and committed. `npm run docs:check` fails, and so does CI, if any generated file is stale.
- The generated pages are listed explicitly in `pages` in `scripts/docs/build.mjs`: `docs/README.md`, REQUIREMENTS, ARCHITECTURE, `systems/*.md`, DEVELOPMENT, `validation/P0-P1.md`, ISSUES, ISSUES_CLOSED, QUALITY, REVIEW and the root `README.md`. A new page must be added to that list. The `CLAUDE.md` files and `AGENTS.md` are not generated pages.
- Editing any generated page rewrites `docs/html/assets/search-index.js` (about 600 KB) as well as the page's HTML. Committing it through the GitHub connector means sending the whole file; see the connector notes in the root CLAUDE.md.
- Regeneration is deterministic. Run `npm run docs:build`, then `npm run docs:check`, and commit the Markdown and HTML together.

## What `docs:check` enforces

- Local links and anchors resolve, there are no duplicate element IDs, there are no external runtime assets, and there are at least five Mermaid diagrams.
- The active overview table in `docs/ISSUES.md` (under `## Work overview`) and the detail headings (`### F-...`) match one to one. Every active detail ID also appears in `docs/REQUIREMENTS.md` (ranges such as `F-055–F-060` count).
- No Done or Closed rows remain in the active overview. Every closed overview row in `docs/ISSUES_CLOSED.md` has every cell struck through (`~~...~~`), a matching detail heading, and a struck-through title after its ID. An ID must not appear in both overviews.
- `scripts/docs/behavior.test.mjs` runs four jsdom checks of search, focus, copy and theme. These are DOM substitutes, not native browser rendering.

## Tracker workflow

- Track work in `docs/ISSUES.md`, never in GitHub Issues. IDs are scoped (`F-OPS-002`, `F-UI-004`, `F-BIRD-001`); never reuse one. Overview columns are `ID | Priority | Type | Item | Status | Depends on`.
- A detail section uses `### <ID> — <title>`, then `**Status:**`, owner, `**Branch:** \`<branch>\``, `**Accept when:**` and dated execution records. The public `tracker/` site takes status from the overview table and branch ownership from the `**Branch:**` line.
- Statuses run Open → In progress → Review → Done, plus Blocked or Deferred. Implemented work stays in Review until the user signs off. A review score is not sign-off.
- Closing an item moves its overview row, detail section, closure date and reason, and related evidence to `docs/ISSUES_CLOSED.md` in the same commit. Strike through the archived cells and title. Reopening reverses the move with a dated reason.

## Keeping records honest

- Append dated sections (`— 19 October 2026`, America/Creston) and state clearly which statement is current. Do not rewrite historical evidence. Mark it superseded instead.
- `docs/QUALITY.md` records runtime batches: branch, base, models and effort, approach, checks with counts, review scores and findings, and validation limits. `docs/REVIEW.md` records documentation reviews. `docs/validation/*.json` holds publication evidence: source SHA, Pages SHA, workflow runs and file hashes.
- Keep source completion, review, publication and user acceptance as separate milestones. Never describe headless or DOM checks as rendered, device or listening evidence.
